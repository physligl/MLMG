\chapter{分布式 GPU 多重网格}
\label{ch:distributed-gpu}

\begin{keybox}
分布式 GPU 不是“MPI + CUDA 两章相加”。它把三种原本分开的概念同时放进一个执行图：
\begin{equation}
\boxed{
\text{rank-level logical ownership}
\quad+\quad
\text{device residency}
\quad+\quad
\text{CPU/GPU/NIC execution dependencies}.
}
\label{eq:distributed-gpu-three-layers}
\end{equation}
对常见的一 rank 一 GPU 配置，\textbf{rank 决定哪些全局 unknowns 属于本进程，GPU 决定这些本地数据主要驻留在哪里、由谁执行 kernel}。只有在一 rank 驱动多个 GPUs 时，才需要进一步把 rank-local state 划分成 device-local ownership。这个区分是理解 GPU-aware halo、coarse redistribution 和多 GPU V-cycle 的起点。
\end{keybox}

\section{逻辑所有权、数据驻留与执行位置}

在\chapref{ch:mpi}中，rank $p$ 的逻辑状态为
\begin{equation}
u_p^{local}
=
\left\{
u_p^{owned},
u_p^{ghost}
\right\}.
\end{equation}
这一 owned/ghost 关系仍然是分布式算法的权威语义。

若采用一 rank 一 GPU，常见实现让这两个数组主要驻留在该 rank 绑定的 device memory 中：
\begin{equation}
\text{global cell}
\rightarrow
\text{owner rank}
\rightarrow
\text{rank-local index}
\rightarrow
\text{device-resident storage}.
\label{eq:distributed-gpu-address-chain}
\end{equation}

最后一条箭头描述的是\textbf{placement}，不是新的数学所有权。换句话说：
\begin{equation}
\boxed{
\text{MPI ownership}
\neq
\text{GPU residency}.
}
\end{equation}

这个区别非常重要。若某个 buffer 暂时被拷到 host，并不会改变它所对应 unknown 的 owner rank；如果一个 rank 同时驱动两块 GPUs，才需要再增加
\begin{equation}
\text{rank-local region}
\rightarrow
\text{device 0/device 1 partition}
\end{equation}
这一层真正影响写入责任的映射。

\section{Rank--Device 映射与资源拓扑}

一 rank 一 GPU 的优点是 owner、device context 与执行队列关系清楚。实际系统仍要保证：
\begin{itemize}
\item rank 与正确 GPU 建立稳定绑定；
\item host thread 尽量位于靠近该 GPU/NIC 的 CPU/NUMA domain；
\item device allocation、pinned host buffer 和 MPI endpoint 的物理位置不要无意跨越远端 socket；
\item 多 rank 共享一 GPU 时明确资源竞争和上下文策略。
\end{itemize}

因此“rank $p$ 使用 GPU $p$”只是逻辑编号规则，不自动保证物理 affinity 正确。多 GPU 性能问题必须同时看进程放置、GPU 拓扑和 NIC 路径。

\section{GPU-Aware 通信}
\label{sec:gpu-aware-path}

\chapref{ch:mpi}已经把 halo 定义为
\begin{equation}
u^{owned,q}
\rightarrow
u^{ghost,p}
\end{equation}
的版本刷新。分布式 GPU 只是在这个数据边上增加了 memory-space 问题。

传统 staged 路径可以抽象为
\begin{equation}
D
\rightarrow
H
\rightarrow
\text{network}
\rightarrow
H
\rightarrow
D,
\label{eq:distributed-gpu-staged-path}
\end{equation}
其中 $D/H$ 分别表示 device/host memory。

若通信栈允许直接使用 device buffer，算法层路径可近似写成
\begin{equation}
D
\rightarrow
\text{network}
\rightarrow
D.
\label{eq:distributed-gpu-direct-path}
\end{equation}
底层是否进一步使用特定 direct-memory/RDMA 机制属于系统实现问题，不能从“MPI 接受 device pointer”这一事实自动推出。

因此 GPU-aware communication 的正确心智模型是：
\begin{equation}
\boxed{
\text{同一 owned-to-ghost 语义}
\quad
\text{采用更短的数据路径}.
}
\end{equation}
它不会减少 halo 数学需求，也不会自动减少 message count。

\section{Pack--Network--Unpack 数据路径}

结构网格的 face/edge 数据在实际布局中未必总是连续发送区。典型 halo 路径可能包含：
\begin{equation}
\text{device pack}
\rightarrow
\text{network transfer}
\rightarrow
\text{device unpack}
\rightarrow
\text{ghost ready}.
\label{eq:distributed-gpu-halo-chain}
\end{equation}

于是 halo 成本至少包含：
\begin{equation}
T_{\mathrm{halo}}
\approx
T_{\mathrm{pack}}
+
T_{\mathrm{network}}
+
T_{\mathrm{unpack}}
+
T_{\mathrm{unhidden\ sync}}.
\end{equation}

如果采用 staged host buffer，还要加入 D2H/H2D 数据搬运。若通信 buffer 可以直接参与网络传输，则这些 host staging 项可以消失或显著改变。

这里不应只测“MPI call time”。一个看似网络慢的 halo，实际瓶颈可能是 device pack kernel、host staging、stream synchronization 或 unpack 后的 readiness wait。

\section{多 GPU V-Cycle 的依赖图}

常见描述会说“device kernel DAG”和“MPI communication DAG”。更准确的模型是：\textbf{整个 V-cycle 只有一张跨资源依赖图，其中不同节点分别由 GPU、CPU runtime、MPI/NIC 执行。}

以 residual 为例：
\begin{equation}
\boxed{
\begin{aligned}
&\text{device pack}
\rightarrow
\text{network}
\rightarrow
\text{device unpack}
\rightarrow
\text{boundary residual},
\\
&\text{interior residual}
\quad\parallel\quad
\text{network path},
\\
&\text{interior ready}
+
\text{boundary ready}
\rightarrow
\text{restriction}.
\end{aligned}
}
\label{eq:distributed-gpu-residual-dag}
\end{equation}

这里的并发不是因为“用了两个 streams”或“用了 nonblocking MPI”，而是因为 interior residual 与远端 halo 在数据依赖上独立。Stream、event、MPI request 只是把这张 DAG 映射到具体 runtime。

因此：
\begin{equation}
\boxed{
\text{asynchronous API}
\neq
\text{automatic overlap}.
}
\end{equation}
若通信不能推进、interior work 太短、pack 占满同一 GPU 资源，或存在隐式 device synchronization，理论上的并行分支仍可能在实际时间线上串行。

\section{四 GPU V-Cycle 示例}
\label{sec:distributed-gpu-trace}

考虑一个 $256^3$ 三维问题，采用 $2\times2\times1$ 空间分区，每个 rank 绑定一块 GPU。细层每个 rank/GPU 约拥有
\begin{equation}
\frac{256^3}{4}
=
4{,}194{,}304
\end{equation}
个 unknowns。

一次 residual/restriction 可以按以下逻辑推进：

\begin{enumerate}
\item 每个 rank 在 GPU 上 pack 当前 owned halo；
\item 发布 device-buffer halo communication；
\item 同时启动不依赖 ghost 的 interior residual；
\item ghost 到达并 unpack 后执行 boundary residual；
\item interior/boundary residual 都 ready 后，restriction 才能消费完整 fine residual。
\end{enumerate}

关键点是 restriction 依赖\textbf{完整 residual 状态}，而 pack 与 interior residual 本身没有直接数据依赖。是否用同一 stream、不同 stream 或其他队列执行，是后端调度选择。

连续三维 full coarsening 时，全局 unknown 数变为
\begin{equation}
256^3
\rightarrow
128^3
\rightarrow
64^3
\rightarrow
32^3
\rightarrow
16^3
\rightarrow\cdots.
\end{equation}
若始终保持四块 GPUs 活跃，则每 GPU unknown 数约为
\begin{equation}
4.19\times10^6,
\quad
5.24\times10^5,
\quad
6.55\times10^4,
\quad
8.19\times10^3,
\quad
1.02\times10^3,\ldots
\end{equation}

因此粗化同时在两个维度耗尽并行度：
\begin{itemize}
\item 单 GPU 内 thread/block 数快速下降；
\item 全局上继续保留全部 ranks/GPUs 的意义也快速下降。
\end{itemize}

\section{Device 并行度与 Rank 并行度}

单 GPU 是否饱和，主要取决于该层有多少 blocks/warps 与每 task work；多 GPU 是否值得全部活跃，则取决于每 device work、message latency、redistribution 与 collective 成本。

可以用一个示意性规则估计目标 GPU 数：
\begin{equation}
P_\ell^{\mathrm{target}}
=
\min
\left(
P_{\ell-1},
\max
\left(
1,
\left\lfloor
\frac{N_\ell}{n_{\mathrm{gpu,min}}}
\right\rfloor
\right)
\right).
\label{eq:distributed-gpu-target-ranks}
\end{equation}
其中 $n_{\mathrm{gpu,min}}$ 是通过 benchmark 得到的效率阈值，而不是算法正确性条件。

即使已经收缩到一块 GPU，继续粗化以后仍会进入低利用率区。因此：
\begin{equation}
\boxed{
\text{rank/device consolidation}
\quad
\text{只能解决跨设备并行度过剩，}
}
\end{equation}
不能解决单 GPU 内部已经没有足够 block 的问题。

\section{Coarse Redistribution 与所有权变换}

若 active GPU/rank 数由
\begin{equation}
4
\rightarrow
2
\rightarrow
1
\end{equation}
收缩，粗层 state 的 MPI owner set 也必须同步变化：
\begin{equation}
\text{fine owner set}
\rightarrow
\text{coarse redistribution}
\rightarrow
\text{coarse owner set}.
\label{eq:distributed-gpu-owner-transition}
\end{equation}

正确性至少要求三件事：

\begin{enumerate}
\item coarse vector/operator/metadata 都使用一致的新 owner mapping；
\item coarse collective 只在正确的 active communicator/rank subset 上执行；
\item V-cycle 回程 prolongation 前，coarse correction 能沿反向映射返回需要它的 fine owners。
\end{enumerate}

因此 rank consolidation 不是“让一些 GPU 休息”，而是 V-cycle 数据模型的一次显式 ownership transformation。

其 break-even 条件仍然是
\begin{equation}
T_{\mathrm{redistribute}}
+
T_{\mathrm{coarse}}(P_{\mathrm{new}})
<
T_{\mathrm{coarse}}(P_{\mathrm{old}}).
\label{eq:distributed-gpu-consolidation-break-even}
\end{equation}

\section{粗网格的双重并行度衰减}

粗层的典型症状是：
\begin{equation}
\boxed{
\text{small kernels}
+
\text{small messages}
+
\text{few blocks}
+
\text{too many active GPUs}.
}
\end{equation}

这四项会形成恶性组合：
\begin{itemize}
\item kernel launch/dispatch 固定成本占比上升；
\item 单 GPU occupancy/grid saturation 下降；
\item halo 消息更容易被 latency 主导；
\item network endpoint 和 collective participant 数仍然过多。
\end{itemize}

因此 coarse strategy 往往需要同时考虑：
\begin{itemize}
\item kernel fusion / graph replay，降低提交固定成本；
\item 一个 thread/block 处理更多 coarse work；
\item 改变 smoother 或 bottom solver；
\item box agglomeration；
\item rank/device consolidation；
\item 必要时 CPU handoff。
\end{itemize}

CPU handoff 不能只看“CPU 对小问题 latency 更低”。必须把
\begin{equation}
T_{D\rightarrow H}
+
T_{\mathrm{CPU\ solve}}
+
T_{H\rightarrow D}
\end{equation}
与留在 GPU 的低利用率 solve 比较。

\section{Global Reduction 与多 GPU Krylov}

多 GPU Krylov+MG 中，一次外层迭代通常包含：
\begin{equation}
\text{operator}
\rightarrow
\text{dot/reduction}
\rightarrow
\text{MG preconditioner}
\rightarrow
\text{vector update}
\rightarrow\cdots
\end{equation}

MG 内部主要含 nearest-neighbor halo 和 coarse redistribution；Krylov dot/norm 则会增加 global collective。两者的通信范围完全不同。

为了避免重叠事件重复计时，可以用互斥 accounting bins 表示 wall time：
\begin{equation}
T_{Krylov}^{\mathrm{wall}}
=
T_{op}^{\mathrm{excl}}
+
T_{global\ reduce}^{\mathrm{excl}}
+
T_{MG\ preconditioner}^{\mathrm{excl}}
+
T_{vector}^{\mathrm{excl}}.
\label{eq:distributed-gpu-krylov-exclusive-cost}
\end{equation}

其中 $\mathrm{excl}$ 的含义是同一段 wall-clock 时间只归到一个阶段。Profiler 中不同 GPU kernels、copies 和 MPI events 若发生 overlap，其 duration 不能直接求和得到 wall time。

这也说明“单 GPU kernel 快了 2 倍但多 GPU solve 只快 8\%”完全可能：真正的 critical path 可能主要由 network、global reduction 或 coarse redistribution 组成。

\section{通信与计算的资源竞争}

即使 DAG 允许 pack/network 与 interior compute 并发，也还要问它们是否竞争同一硬件资源。

例如：
\begin{itemize}
\item pack kernel 与 interior kernel 都需要 GPU memory bandwidth；
\item device copy engine、NIC 与 kernel 可能共享 PCIe/互连路径；
\item pack kernel 占满 SM 或 HBM 后，interior kernel 未必能同时达到原吞吐；
\item 为等待 MPI request 而插入的 device sync 可能阻断 stream overlap。
\end{itemize}

所以理想模型
\begin{equation}
T
\approx
\max(T_{\mathrm{comm}},T_{\mathrm{interior}})
\end{equation}
只是上界目标。真实 overlap 必须从 timeline 验证，而不是从 API 名称推断。

\section{多 GPU V-Cycle 性能诊断}

建议按以下层次定位：

\begin{enumerate}
\item \textbf{rank ownership}：owned/ghost 与 active communicator 是否正确；
\item \textbf{device residency}：热路径是否出现意外 H2D/D2H；
\item \textbf{pack/unpack}：halo 预处理是否已经成为主要 kernel；
\item \textbf{network}：消息大小、数量与 latency/bandwidth；
\item \textbf{overlap}：interior work 是否真的与 network 同时发生；
\item \textbf{resource contention}：pack/network 与 interior 是否争用 HBM、copy engine、PCIe/NVLink 等资源；
\item \textbf{single-GPU coarse utilization}：每层 block 数是否已显著低于设备并行容量；
\item \textbf{multi-GPU coarse utilization}：每 GPU work 是否低到应该 consolidation；
\item \textbf{global collective}：Krylov reductions 是否形成更长 critical path；
\item \textbf{bottom strategy}：继续 GPU、融合、收缩、CPU handoff 中哪条路径实际更快。
\end{enumerate}

这套顺序可以避免把所有问题都归结为“网络慢”或“GPU 利用率低”。

\section{本章小结}

分布式 GPU 多重网格的核心不是两套并行模型并排存在，而是一张跨 rank、device 和 network 的统一依赖图。Rank 决定数值所有权，device 决定主要数据驻留与 kernel 执行位置，GPU-aware communication 只改变 owned-to-ghost 数据路径。

粗化会同时耗尽单 GPU 内 block-level parallelism 和全局 rank/GPU parallelism，因此多 GPU coarse levels 必须同时处理 kernel fixed cost、small-message latency、ownership redistribution 与 active communicator 缩减。最终性能只能通过 end-to-end critical path 判断，而不能由单 kernel 或单 MPI call 独立推断。

\section*{习题}

\subsection*{所有权与数据路径}
\begin{enumerate}[label=\arabic*.]
\item 对一 rank 一 GPU，分别画出 global cell、owner rank、rank-local index、device address 四层映射，并解释哪一层属于逻辑所有权。
\item 设计一 rank 两 GPU 的 rank-local partition，指出此时哪些数据需要增加 device-local ownership/ghost。
\item 一个 device halo 为 8 MB，PCIe D2H/H2D 各 $20\,\mathrm{GB/s}$，网络 $25\,\mathrm{GB/s}$。估算 staged path 的数据搬运下界，并与忽略 host staging 的 direct-device path 比较。
\item 说明为什么 GPU-aware MPI 不改变离散算子结果，只改变式~\eqref{eq:distributed-gpu-staged-path}的数据移动路径。
\end{enumerate}

\subsection*{统一 DAG 与 Overlap}
\begin{enumerate}[label=\arabic*.]
\item 为 residual 写出 device pack、network、unpack、interior residual、boundary residual 和 restriction 的依赖图。
\item pack kernel 为 $8\,\mu s$、network 为 $20\,\mu s$、unpack 为 $6\,\mu s$、interior kernel 为 $30\,\mu s$。计算完全串行与理想 overlap 的阶段时间。
\item 构造一个 DAG 允许 overlap 但实际 timeline 没有 overlap 的案例，分别从通信 progress、GPU resource contention 和隐式 synchronization 解释。
\item 用 profiler 记录 pack、network、unpack、interior、boundary 的时间线，不允许只用各 event duration 求和估计 wall time。
\end{enumerate}

\subsection*{粗层与 Consolidation}
\begin{enumerate}[label=\arabic*.]
\item 对 $256^3$ 全局问题和 4 GPUs，计算连续五层 full coarsening 后每 GPU unknown 数。
\item 给定 $n_{\mathrm{gpu,min}}=16384$，使用式~\eqref{eq:distributed-gpu-target-ranks}设计一个 $4\rightarrow2\rightarrow1$ 的目标 active-GPU 序列。
\item 设 redistribution 需要 $0.6$ ms，4 GPU coarse solve 为 $1.8$ ms，2 GPU coarse solve 为 $0.7$ ms。判断式~\eqref{eq:distributed-gpu-consolidation-break-even}是否满足。
\item 解释为什么已经收缩到单 GPU 后，继续粗化仍会出现 device-level parallelism collapse。
\item 比较“留在单 GPU”“CPU handoff”两条 bottom path，列出 break-even 所需的全部可测时间。
\end{enumerate}

\subsection*{多 GPU Krylov 与诊断}
\begin{enumerate}[label=\arabic*.]
\item 外层 Krylov 每步含 2 次 global reductions，每次 $10\,\mu s$，MG preconditioner 为 $120\,\mu s$。计算 reductions 占简化 iteration 时间的比例。
\item 某 fine-grid kernel 优化 2 倍，但 end-to-end solve 仅改善 8\%。构造一组 exclusive phase accounting 解释这一结果。
\item 设计 rank/device/NIC affinity 检查表，说明如何发现 rank 绑定 GPU 正确但 CPU/NIC 拓扑错误的情况。
\item 对一个 coarse-level 低效率案例，同时记录 blocks/SM、cells/GPU、message size、active ranks、collective time，判断是 device collapse 还是 rank collapse 先出现。
\end{enumerate}
