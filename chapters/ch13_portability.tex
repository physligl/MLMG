\chapter{异构编程模型与性能可移植性}
\label{ch:portability}

\begin{keybox}
性能可移植性不是“同一份源码能编译”这么简单。真正需要保持的是\chapref{ch:mg-parallel-operations}已经确定的\textbf{操作语义、数据所有权和依赖关系}，同时允许不同后端选择不同的执行粒度、memory space 和同步实现。
\end{keybox}

\section{算法接口与执行后端分离}

理想的软件边界不是让数值代码直接写满 OpenMP/CUDA/MPI 细节，而是把核心操作表达成稳定接口，例如：
\begin{align}
&\texttt{apply\_operator(level, u, r)},\qquad
\texttt{smooth(level, u, b)},\\
&\texttt{restrict(transfer, fine, coarse)},\qquad
\texttt{prolong(transfer, coarse, fine)}.
\end{align}
这里的 \texttt{transfer} 不是无语义的函数标签，而是已经固定了 DOF location、quantity semantics、geometry 与离散内积约定的传递算子描述；这一点与\chapref{ch:two-grid}建立的 $R/P$ 数学语义一致。接口固定的是读写集合、数学操作和依赖关系，后端才决定 task 如何映射。

这种分层只有在数据布局也可描述时才成立。单纯抽象 execution policy，却让 host/device memory、ghost ownership、temporary workspace 仍然散落在算法逻辑中，最终仍会形成“可编译但不可维护”的后端分叉。

\section{执行空间与内存空间}

异构抽象至少需要区分两个维度：
\begin{itemize}
\item \textbf{执行空间（execution space）：}任务在 CPU 线程、GPU 线程或其他设备上执行；
\item \textbf{内存空间（memory space）：}数据位于主机内存、设备内存、统一/共享内存，或分布式的 rank-local memory。
\end{itemize}
只有执行位置与数据驻留关系匹配，内核（kernel）才能合法且高效地访问数据。一个可移植多维视图（view/container）的价值，是把形状、步长（stride）和所有权与底层 allocation 绑定，而不是假设所有指针在所有设备上都等价。

\section{并行模式的可移植表达}

最值得抽象的是稳定的并行模式：
\begin{itemize}
\item parallel-for：Jacobi/residual/correction；
\item parallel-reduce：norm/dot；
\item team/tile policy：GPU block 或 CPU tile；
\item memory view：多维索引与 stride；
\item 异步任务与依赖：halo readiness、kernel DAG。
\end{itemize}
对本书当前以规则结构网格为主的 target-centric 实现，restriction/prolongation 常可表达为 gather parallel-for，从而映射到 OpenMP loop、CUDA kernel、HIP/SYCL kernel 或 Kokkos execution policy。但这不是 transfer 的一般定义：更复杂的传递可能表现为 sparse operator apply、scatter/reduction，或同时包含跨 rank 通信；可移植层必须保留这些语义差异。


\section{残差计算的跨后端语义一致性}
\label{sec:portability-residual-trace}

抽象是否有效，最好不要从 API 名字判断，而要跟踪同一个数值操作。设某一层已经完成 halo exchange，需要计算
\begin{equation}
r_i=b_i-(Au)_i
\end{equation}
并保证只写 owned cells。这个操作至少包含四个稳定语义：读取 $u$ 与 $b$，读取相邻 stencil 数据，写入 $r$，以及在 ghost ready 之后才能启动。不同后端改变的是执行粒度和内存位置，而不是这四个语义。

\begin{center}
\begin{tabularx}{0.96\textwidth}{>{\bfseries}p{2.9cm}XXX}
\toprule
对象 & CPU/OpenMP & GPU 原生后端 & 可移植执行层\\
\midrule
迭代域 & owned cells 的并行循环 & grid/block/thread 映射 & parallel-for 的索引空间\\
数据表示 & host-resident view & device-resident view & 带 memory space 的 view\\
前置依赖 & halo 完成后进入并行区 & event/stream 等待 ghost ready & 依赖对象或后端同步语义\\
局部粒度 & chunk/tile/vector width & block size、每线程 cell 数 & team/tile policy 后端特化\\
数值定义 & $r=b-Au$ & $r=b-Au$ & $r=b-Au$\\
\bottomrule
\end{tabularx}
\end{center}

这张表揭示了性能可移植的边界。\textbf{数值层必须稳定的是迭代域、读写集合、依赖关系和离散算子；不应该稳定的是 block size、tile shape 或具体同步原语。}如果为了“统一代码”连这些后端参数也强制相同，抽象就把性能调节能力一并抹掉；反过来，如果数值层直接判断 warp size 或设备型号，抽象又失去了隔离硬件细节的意义。

\paragraph{一个可验证的迁移过程。}
假设先有一个已经验证的 CPU residual 实现。迁移到 GPU 或可移植框架时，不应先比较速度，而应按以下顺序检查：第一，用同一组 $u,b$ 验证输出 $r$ 在允许的舍入误差范围内一致；第二，验证边界/ghost 依赖没有因异步执行发生竞态；第三，再把时间拆成 interior、boundary、同步与数据移动；第四，才比较不同 tile/team 参数。这个顺序把“数值等价”和“执行效率”分开，使性能问题不会被错误地解释成算法差异。

\section{原生后端与可移植框架}

原生 CUDA/HIP 通常提供最直接的设备控制能力；OpenMP target、SYCL、Kokkos 等则提供更统一的执行与内存抽象。选择时应比较的不只是单 kernel 峰值，还包括：
\begin{itemize}
\item 多维 view/layout 是否能表达结构网格和 patch；
\item reduction、team/tile、async dependency 是否自然；
\item host/device/multi-GPU memory management 是否清晰；
\item profiler 与调试工具是否足够；
\item coarse-grid 特殊路径是否允许下沉到原生实现。
\end{itemize}

性能可移植框架不应该迫使所有后端采用同一个 tile size 或完全相同的 kernel fusion。\textbf{语义可移植，调度参数允许后端特化}通常更现实。

\section{避免泄漏硬件细节}

如果数值层开始直接出现“warp size”“具体 GPU 型号”“NUMA node”或特定 MPI communicator/rank 编号等硬件与执行后端判断，说明抽象边界可能已经泄漏。更稳定的做法是数值层表达：
\begin{equation}
\text{parallel-for / reduction / halo dependency / memory view},
\end{equation}
后端层再决定这些语义如何实现。

但抽象也不能抹掉必要信息。例如 line smoother 的任务不是 pointwise；distributed halo 具有 owner/ghost 语义；这些属于算法本身，应保留在接口中，而不是为了“统一 API”伪装成普通 map。


\section{V-Cycle 的分层性能评价}

下面给一个\emph{示意性}例子，说明为什么单个 stencil 的性能比例不足以代表求解器。设某 GPU 上原生后端与可移植后端的一次 V-cycle 时间分解如下：
\begin{center}
\begin{tabular}{lcc}
\toprule
阶段 & 原生后端 / ms & 可移植后端 / ms\\
\midrule
smooth + residual & 3.0 & 3.3\\
restriction/prolongation & 0.8 & 0.9\\
粗层与 bottom solve & 1.5 & 2.4\\
同步与其他开销 & 0.7 & 1.0\\
\midrule
总计 & 6.0 & 7.6\\
\bottomrule
\end{tabular}
\end{center}
细层主 kernel 只慢约 $10\%$，但完整 cycle 慢约 $27\%$。差异主要来自粗层与同步，而不是细层 stencil。因此性能可移植性至少要同时回答两个问题：\textbf{热点 kernel 是否接近平台最佳，以及完整求解流程是否仍能控制粗层、同步和数据驻留。}

\section{性能可移植性的评价}

先定义单个平台 $a$ 上的\textbf{归一化效率} $e_a$。若性能指标 $P$ 是越大越好，例如 throughput，可写成
\begin{equation}
e_a=\frac{P_{portable,a}}{P_{best,a}}.
\label{eq:portability-platform-efficiency-throughput}
\end{equation}
若评价对象是 time-to-solution，则更自然地写成
\begin{equation}
e_a=\frac{T_{best,a}}{T_{portable,a}},
\label{eq:portability-platform-efficiency-time}
\end{equation}
使得两种定义都满足 $0<e_a\le1$。这里的 $P_{best,a}$ 或 $T_{best,a}$ 必须来自同一个数值问题、同一精度目标和预先声明的参考实现集合，否则归一化本身就不可比较。

单个平台的 $e_a$ 仍不是跨平台 performance portability。Pennycook、Sewall 与 Lee 提出的经典指标在目标平台集合 $\mathcal A$ 上使用效率的调和平均，并把目标平台上不能运行显式视为零 portability\cite{pennycook2019performance}：
\begin{equation}
\Phi(\mathcal A)=
\begin{cases}
\displaystyle
\frac{|\mathcal A|}
{\sum_{a\in\mathcal A}1/e_a},
& \text{若所有 }a\in\mathcal A\text{ 都受支持},\\[1.0em]
0,
& \text{否则}.
\end{cases}
\label{eq:portability-pennycook-metric}
\end{equation}
这个定义的价值不在于宣称一个标量足够描述所有可移植性，而在于同时惩罚低效率平台和缺失平台；实际分析仍应保留各平台的 $e_a$ 分布。

对 multigrid，$e_a$ 的评价对象也不应只是单个 fine-grid kernel，而应是完整、数值等价的 V-cycle 或 solve。特别是在异步后端中，不能把所有 kernel/MPI event duration 简单相加作为总时间。按照\chapref{ch:benchmarking}的计时约定，应直接测量
\begin{equation}
T_{solve}^{\mathrm{wall}},
\end{equation}
并把 level/operation 数据作为 exclusive accounting 或可重叠 event duration 分别报告。一个框架若细层 stencil 很快但无法控制粗层重分布，完整 solve 的 $e_a$ 仍可能很低。

\section{本章小结}

异构可移植性的核心是稳定算法语义与可替换执行后端：任务、ownership、memory view、reduction 与 halo dependency 必须被清楚表达；tile、thread/block、stream 和后端调优参数则允许特化。真正的评价对象是完整 V-cycle/solve，而不是某个孤立 kernel 能否跨平台运行。

\section*{习题}
\subsection*{抽象边界与性能模型}
\begin{enumerate}[label=\arabic*.]
\item 某 portable backend 在 CPU/GPU 上分别达到各自原生最佳 time-to-solution 效率的 85\%/72\%。按式~\eqref{eq:portability-pennycook-metric}计算两平台 performance portability；再计算算术平均与几何平均，并比较三种聚合方式对低效率平台的敏感性。
\item 给定 V-cycle 五类 operation 时间，分别计算两个后端的 total cycle time，判断单独 stencil 快 20\% 是否足以让整体更快。
\item 一个 backend 需要每 cycle 额外做两次 host-device sync，各 15 $\mu$s。计算在 100 $\mu$s 与 2 ms cycle 上的相对开销。

\item 说明为什么 execution-space 抽象不能自动解决 memory-space 正确性。
\item 给出“语义可移植、调度参数后端特化”不会改变数值结果的条件。
\item 构造一个反例说明：如果 abstraction 既不向数值层暴露 halo/ownership 语义，也没有在运行时内部编码相应的通信与依赖，那么仅靠 local parallel-for 不能保证分布式 stencil 的全局正确性。再说明为什么“隐藏具体 MPI rank”本身并不违反这一条件。
\end{enumerate}
\subsection*{跨后端验证}
\begin{enumerate}[label=\arabic*.]
\item 为 residual/restriction/prolongation 设计统一 kernel interface，并实现两个执行后端。
\item 比较 AoS/SoA 或不同多维 layout 在 CPU/GPU 上的影响。
\item 为同一 V-cycle 收集 backend-neutral phase timing。
\end{enumerate}
\subsection*{可移植性决策}
\begin{enumerate}[label=\arabic*.]
\item 设计一个 backend abstraction，明确哪些概念必须暴露给数值层、哪些必须隐藏。
\item 评审一个“所有硬件统一 tile size”的方案，指出性能可移植性风险。
\item 为软件库选择原生 CUDA/HIP、OpenMP target、SYCL 或 Kokkos 时制定评价矩阵。
\end{enumerate}
