\chapter{并行计算的基本模型}
\label{ch:parallel-model}

\begin{keybox}
\textbf{本章建立一套先于 OpenMP、CUDA 与 MPI 的并行分析语言。}并行程序不应从“开多少线程”开始理解，而应沿着
\begin{equation}
\boxed{
\text{数值问题与语义}
\rightarrow
\text{算法}
\rightarrow
\text{逻辑任务与状态版本}
\rightarrow
\text{计算依赖图}
\rightarrow
\text{数据所有权与放置}
\rightarrow
\text{调度}
\rightarrow
\text{机器执行}
}
\label{eq:parallel-analysis-chain}
\end{equation}
逐层分析。算法、逻辑任务与计算依赖图决定算法本身暴露多少并行性，数据层决定哪些读取会跨越所有权或地址空间边界，最后才轮到线程、warp、rank、cache、NUMA 与网络。本章的目标不是记忆并行 API，而是形成一种可以迁移到任意数值 kernel 的诊断方法。
\end{keybox}

\section{逻辑任务、状态版本与读写集合}

并行分析的第一步不是把一段串行代码逐行分给多个执行单元，而是先确定：\textbf{这个算法由哪些逻辑任务组成，每个任务读取什么状态、产生什么新状态。}只有把这一层说明白，后面讨论依赖、并行度和调度才有明确对象。

考虑向量更新
\begin{equation}
y_i^{new}=a x_i+y_i^{old}.
\label{eq:parallel-vector-update}
\end{equation}
可以把“产生第 $i$ 个 $y_i^{new}$”看成一个逻辑任务 $t_i$。对任务 $t$ 定义读集合 $R_t$ 与写集合 $W_t$，于是
\begin{equation}
R_{t_i}=\{x_i,y_i^{old}\},
\qquad
W_{t_i}=\{y_i^{new}\}.
\end{equation}
不同 $i$ 的任务读取和写入不同状态，因此可以彼此独立。

再看一维三点算子
\begin{equation}
z_i=x_{i-1}-2x_i+x_{i+1}.
\label{eq:parallel-three-point}
\end{equation}
相邻任务会读取重叠的 $x$，但各自只写自己的 $z_i$。这说明一个后面反复使用的事实：
\begin{equation}
\boxed{
\text{共享读取不产生先后依赖；冲突来自状态的产生、消费与覆盖。}
}
\label{eq:parallel-shared-read}
\end{equation}

这里还必须区分\textbf{变量名}和\textbf{状态版本}。迭代程序的源码可能一直使用变量名 \texttt{x}，但逻辑上
\begin{equation}
x^{(0)},x^{(1)},x^{(2)},\ldots
\end{equation}
是不同状态。后一个状态由前一个状态产生，不能因为物理实现复用了同一块内存，就把它们在算法分析中视为同一个对象。Jacobi 中的 old/new buffer、时间推进中的 $u^n/u^{n+1}$、Krylov 方法中的不同迭代向量都属于这一类。

两个任务访问同一存储位置时，常见的数据危险可以分为：
\begin{itemize}
\item read-after-write（RAW）：后一个任务读取前一个任务产生的新值，是数据流上的\textbf{真依赖}；
\item write-after-read（WAR）：后一个任务要覆盖某个位置，但前一个任务尚未完成对旧值的读取，是\textbf{反依赖}；
\item write-after-write（WAW）：两个任务都会写同一位置，需要确定最终写入关系；
\item read-after-read（RAR）：双方都只读，不产生顺序约束。
\end{itemize}

RAW 通常反映算法真正的数据流。WAR 与 WAW 则经常来自物理存储复用，可以通过 renaming、double buffering、privatization 或给不同状态分配独立输出位置消除。

例如若把式~\eqref{eq:parallel-three-point}改成原地更新
\begin{equation}
x_i\leftarrow x_{i-1}-2x_i+x_{i+1},
\end{equation}
相邻任务可能读取到本 sweep 已被其他任务覆盖的新值。这里新增的顺序约束并不是“三点差分”这一数学关系本身要求的，而是由原地存储策略引入的。后面讨论 Jacobi 与 Gauss--Seidel 时会再次看到同一差别。

\section{计算依赖图}

前面的读写集合给出了任务之间可能发生依赖的原因。现在把这些先后约束组织成一个统一对象。

\begin{keybox}
\textbf{计算依赖图（computation DAG）}记为
\begin{equation}
G=(V,E).
\end{equation}
顶点 $v\in V$ 表示一次\textbf{逻辑计算任务}；有向边
\begin{equation}
u\rightarrow v
\end{equation}
表示在当前算法和状态表示下，任务 $v$ 的合法执行必须等待任务 $u$ 完成。除非特别说明，本书的 DAG 节点表示任务，而不是数组、变量或数据对象。
\end{keybox}

这个定义包含三个容易被忽略的限定。

第一，边表示的是\textbf{必须保持的先后关系}，而不是“两个任务访问了相关数据”。两个任务可以读取同一个输入而没有边；只有当一个任务需要另一个任务尚未产生的状态，或者必须避免覆盖仍会被读取的状态时，才产生顺序约束。

第二，边有方向。若
\begin{equation}
u\rightarrow v,
\end{equation}
含义是 $v$ 等待 $u$，并不意味着 $u$ 也等待 $v$。方向记录了状态从生产者流向消费者的时间关系。

第三，图是无环的。若出现
\begin{equation}
u\rightarrow v\rightarrow w\rightarrow u,
\end{equation}
则三个任务互相等待，没有任何一个可以首先执行。实际程序当然可以有循环，但分析有限次执行时，应把不同迭代的任务实例和状态版本展开。例如
\begin{equation}
x^{(k+1)}=F(x^{(k)})
\end{equation}
对应的是
\begin{equation}
x^{(0)}
\rightarrow
x^{(1)}
\rightarrow
x^{(2)}
\rightarrow\cdots,
\end{equation}
而不是一个抽象的 $x\rightarrow x$ 自环。

\subsection{一个可完全检查的 DAG}

考虑四个逻辑任务：
\begin{align}
t_0 &: a=x_0+x_1,\\
t_1 &: b=x_2+x_3,\\
t_2 &: c=a+b,\\
t_3 &: d=c\,x_4.
\end{align}
其中
\begin{equation}
R_{t_2}=\{a,b\},
\qquad
W_{t_2}=\{c\}.
\end{equation}
由于 $t_2$ 必须等待 $t_0,t_1$ 产生 $a,b$，而 $t_3$ 又要读取 $t_2$ 产生的 $c$，所以依赖边为
\begin{equation}
t_0\rightarrow t_2,
\qquad
t_1\rightarrow t_2,
\qquad
t_2\rightarrow t_3.
\label{eq:parallel-small-dag}
\end{equation}
$t_0$ 与 $t_1$ 之间没有边，因此它们可以并发执行。

为了描述一个 DAG 在某一时刻真正暴露出的并行性，定义\textbf{就绪任务集合（ready set）}：所有前驱任务都已经完成、因而现在可以合法开始执行的任务集合。

在式~\eqref{eq:parallel-small-dag}中，初始 ready set 为
\begin{equation}
\mathcal R_0=\{t_0,t_1\}.
\end{equation}
若先完成 $t_0$，$t_2$ 仍然不能执行，因为 $t_1$ 尚未完成；当 $t_0,t_1$ 都完成以后，
\begin{equation}
\mathcal R=\{t_2\},
\end{equation}
最后才轮到 $t_3$。

因此调度器能做的事情存在一个严格边界：
\begin{equation}
\boxed{
\text{DAG 决定哪些任务已经可以执行，调度器只决定把这些 ready tasks 分给谁。}
}
\label{eq:parallel-dag-vs-scheduler}
\end{equation}
如果某一时刻 ready set 只有一个任务，即使机器有一万个核心，也只能推进这一条依赖链；如果 ready set 中有一万个任务而机器只有 32 个执行单元，这时才是调度策略和硬件资源数量的问题。

\subsection{问题、算法、计算依赖图与调度}

计算依赖图不是数学问题唯一自带的一张图。更准确的关系是
\begin{equation}
\boxed{
\text{Problem}
\rightarrow
\text{Algorithm}
\rightarrow
\text{Computation DAG}
\rightarrow
\text{Schedule}
\rightarrow
\text{Machine Execution}.
}
\label{eq:parallel-problem-algorithm-dag}
\end{equation}

同一个数学问题可以有多个算法；同一个算法还可能因为状态版本、任务粒度和存储组织不同而得到不同的 computation DAG；固定一个 DAG 以后，又可以有许多合法 schedule。并行算法设计的一个核心任务，就是在保持所需数值语义的前提下，选择具有更有利依赖结构的算法和状态表示，而不是只在一张固定 DAG 上寻找调度技巧。

\section{Work、Span 与并行度}

给 DAG 中每个任务 $v$ 一个执行代价 $w(v)>0$。所有任务代价之和定义为 work：
\begin{equation}
\boxed{
W=\sum_{v\in V}w(v).
}
\label{eq:parallel-work}
\end{equation}
它表示完成这次计算总共需要做多少逻辑工作。

DAG 中任意一条有向路径都对应一串必须严格按顺序完成的任务。所有路径中总代价最大的一条称为\textbf{关键路径（critical path）}，其代价定义为 span：
\begin{equation}
\boxed{
S=
\max_{\pi\in\operatorname{Paths}(G)}
\sum_{v\in\pi}w(v).
}
\label{eq:parallel-span}
\end{equation}

若式~\eqref{eq:parallel-small-dag}中的四个任务代价都为 1，则
\begin{equation}
W=4.
\end{equation}
最长路径可以是
\begin{equation}
t_0\rightarrow t_2\rightarrow t_3
\end{equation}
或
\begin{equation}
t_1\rightarrow t_2\rightarrow t_3,
\end{equation}
所以
\begin{equation}
S=3.
\end{equation}
即使有无限多个处理器，这个计算也至少需要三个单位时间。第一阶段可以并行执行 $t_0,t_1$，之后仍必须顺序完成 $t_2,t_3$。

算法提供的平均并行度定义为
\begin{equation}
\boxed{
\mathcal P=\frac{W}{S}.
}
\label{eq:parallel-average-parallelism}
\end{equation}
这里的 $\mathcal P$ 是算法/DAG 的属性，不是机器拥有的处理器数量。还要注意，它只是\textbf{平均}并行度：实际 ready-set 大小会沿执行过程变化，局部阶段可能远高于或远低于 $W/S$。

对拥有 $P$ 个执行单元的任意调度，都有两个不可突破的下界。总 work 至少需要由 $P$ 个执行单元分摊，因此
\begin{equation}
T_P\ge\frac{W}{P};
\end{equation}
关键路径中的任务又不能彼此并行，因此
\begin{equation}
T_P\ge S.
\end{equation}
合并得到
\begin{equation}
\boxed{
T_P\ge\max\left(\frac{W}{P},S\right).
}
\label{eq:parallel-lower-bound}
\end{equation}

在理想化的贪心调度模型中，还可以得到 Brent 型上界
\begin{equation}
T_P
\le
\frac{W-S}{P}+S
\le
\frac{W}{P}+S.
\label{eq:parallel-brent-bound}
\end{equation}
这说明 $W$ 与 $S$ 分别控制两个不同极限：处理器数量较少时，时间主要受 $W/P$ 限制；处理器很多时，时间逐渐逼近不能被并行化掉的 span。

因此：
\begin{itemize}
\item 当 $P\ll W/S$ 时，增加执行单元仍可能显著降低时间；
\item 当 $P\gtrsim W/S$ 时，critical path 开始主导；
\item 若实测 $T_P$ 远大于这两个算法级界限，问题通常已经进入 memory traffic、同步、通信、调度或负载不均衡层面。
\end{itemize}

实际性能分析还常用 speedup 与 parallel efficiency：
\begin{equation}
\operatorname{Speedup}(P)=\frac{T_1}{T_P},
\qquad
E_P=\frac{T_1}{P T_P}.
\end{equation}
在抽象 DAG 模型中，若单处理器按所有任务顺序执行，可以把 $T_1$ 与 $W$ 对应起来；真实机器上的单线程和多线程却可能拥有不同 cache、内存带宽、频率和运行时开销，因此\textbf{实测 $T_1$ 不应机械等同于抽象 work}。

Amdahl 定律可以看成对整个 DAG 结构的进一步粗化。若固定问题规模下，基准时间中比例 $s$ 被视为始终串行，其余部分理想地按 $P$ 倍缩放，则
\begin{equation}
\operatorname{Speedup}(P)
\le
\frac{1}{s+(1-s)/P}.
\end{equation}
它适合描述固定实现的强缩放上限，却不能把 $s$ 当成数学问题不可改变的自然常数。下一节会看到，改变算法本身就可能改变依赖图和 span。

\section{依赖图重构与并行算法}

有了 computation DAG 以后，可以更精确地描述一个常见误区：\textbf{并行化并不只是给一张固定 DAG 增加处理器。}算法本身决定 DAG，而算法设计可以改变哪些中间量被计算、以什么顺序组合、哪些状态被保存，从而改变依赖结构。

\subsection{串行前缀和的链式依赖图}

以前缀和（prefix sum，亦称 scan）为例。给定
\begin{equation}
x_0,x_1,\ldots,x_{N-1},
\end{equation}
目标是得到
\begin{equation}
y_i=\sum_{j=0}^{i}x_j,
\qquad
0\le i<N.
\label{eq:parallel-prefix-target}
\end{equation}

最直接的算法是
\begin{equation}
y_0=x_0,
\qquad
y_i=y_{i-1}+x_i.
\label{eq:parallel-prefix-serial}
\end{equation}
对应的核心依赖链是
\begin{equation}
y_0
\rightarrow
y_1
\rightarrow
y_2
\rightarrow\cdots\rightarrow
y_{N-1}.
\label{eq:parallel-prefix-chain}
\end{equation}
因此
\begin{equation}
W=\Theta(N),
\qquad
S=\Theta(N),
\qquad
\frac{W}{S}=\Theta(1).
\end{equation}

这里给每个 $i$ 预先分配一个线程没有任何帮助。问题不在“线程不够”，而在任意时刻几乎只有一个新的 $y_i$ 进入 ready set。式~\eqref{eq:parallel-prefix-chain}描述的是\textbf{这一个递推算法}的 DAG，而不是 prefix sum 问题唯一可能的 DAG。

\subsection{Hillis--Steele Scan 的 Work--Span 特征}

加法满足结合律，因此不必严格沿
\begin{equation}
((x_0+x_1)+x_2)+\cdots
\end{equation}
这一种括号结构计算前缀和。一个直接的并行构造是把状态按轮次展开：
\begin{equation}
y_i^{(0)}=x_i,
\end{equation}
并在第 $k$ 轮计算
\begin{equation}
y_i^{(k+1)}
=
\begin{cases}
y_i^{(k)}, & i<2^k,\\[0.3em]
y_i^{(k)}+y_{i-2^k}^{(k)}, & i\ge 2^k.
\end{cases}
\label{eq:parallel-hillis-steele}
\end{equation}

对 $N=8$，只需要三轮：
\begin{equation}
\text{distance }1
\rightarrow
\text{distance }2
\rightarrow
\text{distance }4.
\end{equation}
同一轮内所有 $i$ 都只读取上一轮状态，因此这些任务可以并行。状态版本
\begin{equation}
y^{(k)}
\rightarrow
y^{(k+1)}
\end{equation}
把不同轮次之间的 RAW 依赖保留下来，却去掉了单轮内部的链式依赖。

这样得到
\begin{equation}
S=\Theta(\log N).
\end{equation}
代价是每一轮仍有 $\Theta(N)$ 个更新，共有 $\Theta(\log N)$ 轮，所以
\begin{equation}
W=\Theta(N\log N).
\end{equation}

这个例子非常重要，因为它说明：
\begin{equation}
\boxed{
\text{减小 span 可以通过增加 work 实现。}
}
\label{eq:parallel-work-span-tradeoff}
\end{equation}
Hillis--Steele scan 的并行深度很小，但它不是 work-efficient 算法。

\subsection{Work-Efficient Scan 的树形结构}

还能不能既保持
\begin{equation}
W=\Theta(N)
\end{equation}
又把 span 降到
\begin{equation}
S=\Theta(\log N)?
\end{equation}
可以。关键是把“所有前缀”拆成两个树形阶段。

仍以 $N=8$ 为例。Up-sweep 先计算越来越大的区间和：
\begin{align}
s_{0:1}&=x_0+x_1,
&
s_{2:3}&=x_2+x_3,
&
s_{4:5}&=x_4+x_5,
&
s_{6:7}&=x_6+x_7,
\\
s_{0:3}&=s_{0:1}+s_{2:3},
&
s_{4:7}&=s_{4:5}+s_{6:7},
\\
s_{0:7}&=s_{0:3}+s_{4:7}.
\end{align}
第一层四个任务并行，第二层两个任务并行，第三层一个任务。Up-sweep 共执行 $N-1$ 次二元合并，深度为 $\log_2N$。

仅有总和还不够，因为我们需要每一个 prefix。Down-sweep 从根节点携带一个“这个区间之前已经累计了多少”的值向下传播。若某个区间节点由左子区间 $L$ 和右子区间 $R$ 组成，并且进入该节点的前缀为 $p$，则
\begin{equation}
p_L=p,
\qquad
p_R=p+s_L,
\label{eq:parallel-downsweep-rule}
\end{equation}
其中 $s_L$ 是 up-sweep 已经算好的左子树总和。

根节点从
\begin{equation}
p_{0:7}=0
\end{equation}
开始。传播到叶子以后，第 $i$ 个叶子的 $p_i$ 正好是
\begin{equation}
p_i=\sum_{j=0}^{i-1}x_j,
\end{equation}
即 exclusive scan；最后再做一次完全并行的
\begin{equation}
y_i=p_i+x_i
\end{equation}
即可得到式~\eqref{eq:parallel-prefix-target}的 inclusive scan。

Up-sweep 与 down-sweep 都只有 $\Theta(\log N)$ 层，每层中的不同树节点可以并发执行；总二元合并次数仍为 $\Theta(N)$。因此
\begin{equation}
\boxed{
W=\Theta(N),
\qquad
S=\Theta(\log N).
}
\label{eq:parallel-work-efficient-scan}
\end{equation}

这时真正改变的不是处理器数量，而是计算结构：
\begin{equation}
\boxed{
\text{linear chain}
\rightarrow
\text{balanced tree}.
}
\label{eq:parallel-chain-to-tree}
\end{equation}
串行递推、Hillis--Steele scan 和 work-efficient tree scan 求解的是同一个数学问题，却对应三张不同的 computation DAG。

\subsection{三种前缀和算法的复杂度}

\begin{center}
\small
\begin{tabularx}{0.94\textwidth}{>{\bfseries}p{3.1cm}XXX}
\toprule
算法 & Work & Span & 结构特征\\
\midrule
串行递推 & $\Theta(N)$ & $\Theta(N)$ & 线性依赖链\\
Hillis--Steele scan & $\Theta(N\log N)$ & $\Theta(\log N)$ & 多轮并行，增加 work 换 span\\

\bottomrule
\end{tabularx}
\end{center}

这个表还揭示了一个容易误解的点：平均并行度 $W/S$ 不是单独评价算法优劣的指标。Hillis--Steele 的 $W/S=\Theta(N)$，甚至高于 work-efficient scan 的 $\Theta(N/\log N)$，但前者做了额外的 $\log N$ 倍级工作。并行算法设计必须同时看 work、span、memory traffic、同步和目标机器，而不能只最大化“可并行任务数”。

\subsection{依赖图重构的数值语义}

上面的树形重排依赖于运算的代数性质。对一般 scan，二元运算 $\oplus$ 至少需要满足适合重括号化的结合性质，才能把
\begin{equation}
((x_0\oplus x_1)\oplus x_2)\oplus\cdots
\end{equation}
重写成树形组合而保持数学结果。

IEEE 浮点加法并不严格满足结合律：
\begin{equation}
\operatorname{fl}((a+b)+c)
\neq
\operatorname{fl}(a+(b+c)).
\end{equation}
因此在浮点计算中，更准确的说法不是“重构 DAG 后输出逐位不变”，而是：
\begin{equation}
\boxed{
\text{在允许的代数变换和数值误差模型下保持问题语义。}
}
\label{eq:parallel-semantic-equivalence}
\end{equation}
若应用要求 bitwise reproducibility，就必须进一步约束 reduction/scan tree 或采用可重复归约方法。

\subsection{多重网格中的依赖图重构}

Prefix scan 只是一个可以完全检查的例子。后续多重网格中会反复出现同一种设计思想。

Jacobi 通过区分 $u^{(k)}$ 与 $u^{(k+1)}$，用额外存储消除原地更新可能产生的 WAR/WAW，使同一 sweep 的输出任务彼此独立。Red--black Gauss--Seidel 利用 stencil 耦合图的着色，把长顺序依赖组织成少数颜色阶段。Reduction 把线性累加重排为树。MPI stencil 把任务细分为 interior 与 boundary 两类，使不依赖 ghost 的 interior work 与通信成为 DAG 中可以并发推进的两条分支。

这些方法改变的对象并不完全相同：有的改变算法，有的改变状态表示，有的只是细化任务粒度。但它们都遵循同一个分析原则：
\begin{equation}
\boxed{
\text{先识别哪些边是真正必须保留的，再判断能否通过算法或表示重构减少关键路径。}
}
\label{eq:parallel-dag-design-principle}
\end{equation}

\section{任务粒度与数据所有权}

依赖 DAG 说明“哪些事情可以并发”，但它并没有规定“一个执行单元一次拿多少事情做”。这里必须区分\textbf{逻辑任务}与\textbf{调度单元}。

对一个 $N$ 点 stencil，可以把“计算一个输出点”定义为最小逻辑任务；真正运行时却可能把连续 $g$ 个点组合成一个 chunk 或 tile 再交给某个 worker。粒度变大通常减少调度、同步和元数据开销，并改善局部性；粒度过大又会减少可调度单元数量，使负载不均更难被隐藏。因此任务粒度本身就是设计变量，而不是由数学公式自动给出的常数。

数据侧还需要区分三个容易混淆的概念：
\begin{enumerate}
\item \textbf{逻辑所有权}：某个阶段结束时，谁对一个输出位置的最终值负责；
\item \textbf{物理放置}：这组字节实际位于哪个 NUMA node、device memory 或 rank address space；
\item \textbf{执行分配}：当前由哪个 thread、block、worker 或 rank-local loop 执行某个任务。
\end{enumerate}

三者并不等价。共享内存程序可以让所有线程都访问同一个数组，但仍规定每个输出区间只有一个 writer；动态调度又可以让不同 worker 在不同时刻执行这些区间。MPI 中则更常见“逻辑所有权”和“地址空间所有权”重合：rank $p$ 拥有自己的 subdomain，其他 rank 若需要读取，就必须通过通信得到副本。

对许多数值 kernel，最重要的正确性规则可以压缩成一句话：
\begin{equation}
\boxed{
\text{阶段内尽量让每个输出位置有唯一 writer，}
\quad
\text{跨所有权读取显式处理。}
}
\end{equation}
这条规则会在共享内存中表现为写区间划分，在 GPU 中表现为 thread/block 到输出的映射，在分布式内存中表现为 owned/ghost 数据模型。

\section{基本数据流模式}

与其从具体 API 记忆并行写法，不如先识别 kernel 属于哪种数据流模式。

\subsection{Map 与 Stencil}

Map 的典型形式是
\begin{equation}
y_i=F(x_i),
\end{equation}
每个输出只依赖同位置输入。若不同 $i$ 写不同输出，它几乎没有算法级依赖。

Stencil 允许读取局部邻域：
\begin{equation}
y_i=F\bigl(\{x_j:j\in\mathcal N(i)\}\bigr).
\end{equation}
只要输入在这一阶段保持只读、输出唯一写入，stencil 同样具有点级并行性。它与 map 的关键差异不是“能不能并行”，而是邻域读取带来的 cache footprint、halo/ghost 需求与边界处理。

\subsection{Gather 与 Scatter}

Gather 让一个输出任务主动读取若干输入：
\begin{equation}
y_i=\sum_{j\in\mathcal S(i)}w_{ij}x_j.
\end{equation}
只要每个 $y_i$ 有唯一 writer，多个任务之间可以共享输入而不发生写冲突。Restriction、SpMV 与很多 stencil 本质上都可以看成 gather。

Scatter 则由一个输入任务向多个输出贡献：
\begin{equation}
y_j\mathrel{+}=g_{ij}x_i.
\end{equation}
多个输入任务可能碰撞到同一个 $y_j$。常见处理并不只有 atomic：还可以做 coloring、thread-private accumulation、分块局部归并，或把数据流反转成等价 gather。\textbf{Atomic 解决的是更新正确性，不会把冲突写自动变成无代价的独立任务。}

\subsection{Reduction 与 Scan}

Reduction 把许多局部值聚合为少量输出，例如
\begin{equation}
\|r\|_2^2=\sum_i r_i^2.
\end{equation}
局部平方具有大量并行性，但聚合阶段需要一棵 reduction tree，因此存在 $\Theta(\log N)$ 级 span；跨 rank 时还会映射为 collective communication。

并行 reduction 还暴露出一个数值计算中非常重要的语义问题：\textbf{树形重排是否合法，取决于归约运算的代数性质。}整数加法在不溢出的数学模型中满足结合律，而 IEEE 浮点加法严格来说不满足
\begin{equation}
(a+b)+c=a+(b+c).
\end{equation}
因此不同线程数、不同 reduction tree 或不同 rank 拓扑可能得到末位不同的结果。若应用要求 bitwise reproducibility，就需要固定归约树或采用专门的可重复归约方法；不能把“无 data race”直接等同于“结果逐位确定”。

Scan 的完整 DAG 重构已经在前面的 prefix-sum 例子中展开。本节只需保留其数据流分类：reduction 只保留最终聚合结果，scan 则保留所有前缀结果；二者都可以利用树结构降低依赖深度，但具体 work/span 取决于所选算法。

\section{同步与通信}

依赖 DAG 只规定先后关系，并没有指定用哪种机制实现它。把 DAG 映射到具体机器以后，一条依赖边才会变成 barrier、atomic、event、message completion 或 collective。

这里最好把\textbf{同步}与\textbf{通信}分开理解。同步首先解决的是“什么时候可以继续”和“前一个任务的写入何时对后一个任务可见”；通信解决的是“所需数据怎样跨越地址空间或物理放置边界到达使用者”。共享内存中的 barrier 可能不复制任何数组，MPI halo exchange 则同时包含数据移动与完成条件。

对于点到点通信，最常用的第一阶模型是
\begin{equation}
T_{\mathrm{msg}}\approx\alpha+\beta m,
\label{eq:parallel-alpha-beta}
\end{equation}
其中 $\alpha$ 表示启动延迟，$m$ 是消息字节数，$\beta$ 是每字节传输时间。若总数据量 $M$ 被拆成 $k$ 个不能完全重叠的小消息，粗略成本会接近
\begin{equation}
k\alpha+\beta M.
\end{equation}
这解释了为什么“总字节数一样”并不意味着通信成本一样：消息数量、拓扑、并发程度与拥塞都会影响实际时间。

异步接口也不自动等于通信已经被隐藏。要真正产生 overlap，至少需要同时满足两点：通信能够由硬件/runtime 向前推进，并且当前关键路径上存在\textbf{与这批远端数据无关的独立 work}。如果发布 nonblocking communication 后立刻等待，程序的 DAG 并没有获得新的可重叠区间。

局部性可以放进同一框架理解。只要一个任务反复读取靠近自己的数据，cache、NUMA local memory、GPU shared memory 或 device HBM 才可能提供高有效带宽。因而并行划分始终在两个目标之间权衡：
\begin{equation}
\boxed{
\text{足够多的独立任务}
\quad\text{与}\quad
\text{足够好的数据局部性和较少的跨边界访问}.
}
\end{equation}

\section{并行计算的机器成本模型}

Work/span 回答“算法最多能提供多少并行”；它不回答一个 task 在真实机器上执行得有多快。到了机器层，至少还要考虑计算吞吐、内存流量、同步/通信固定成本、调度粒度与负载均衡。

对一个主要受计算与内存系统约束的 kernel，令浮点工作量为 $F$、从相关内存层实际搬运的字节数为 $Q$，算术强度定义为
\begin{equation}
I=\frac{F}{Q}.
\end{equation}
若硬件峰值计算率为 $F_{\max}$，可持续内存带宽为 $B_{\max}$，Roofline 给出性能上界
\begin{equation}
\boxed{
P_{\mathrm{kernel}}
\le
\min(F_{\max},I B_{\max}).
}
\label{eq:parallel-roofline}
\end{equation}
这里的 $P_{\mathrm{kernel}}$ 是计算性能，不是处理器数量。Roofline 告诉我们一个 kernel 更可能受 FLOPs 还是 bytes 限制，却不包含 barrier、MPI latency、kernel launch 或 reduction critical path。

因此对一个并行阶段，更稳健的诊断模型不是把所有成本机械相加，而是先区分\textbf{可重叠的资源瓶颈}和\textbf{无法隐藏的协调成本}：
\begin{equation}
\boxed{
T_{\mathrm{stage}}
\approx
\max\!\left(
T_{\mathrm{compute}},
T_{\mathrm{memory}},
T_{\mathrm{dependency}}
\right)
+T_{\mathrm{coord}}^{\mathrm{unhidden}}
+T_{\mathrm{imbalance}}.
}
\label{eq:parallel-cost-decomposition}
\end{equation}
其中 $T_{\mathrm{dependency}}$ 代表由 span、串行段或冲突更新形成的不可并行部分；$T_{\mathrm{coord}}^{\mathrm{unhidden}}$ 包含没有被其他 work 覆盖掉的 barrier、communication、launch 与调度固定成本；$T_{\mathrm{imbalance}}$ 表示最快 worker 完成以后仍需等待最慢 worker 的尾部时间。式~\eqref{eq:parallel-cost-decomposition}仍是诊断模型而非严格恒等式，但它比“FLOPs 决定时间”更接近真实并行执行。

把几个模型放在一起，可以形成清晰分工：
\begin{itemize}
\item work/span 判断算法是否有足够独立性；
\item task granularity 与 ownership 判断任务怎样被组织和谁等待谁；
\item Roofline 判断局部 kernel 的 compute/memory 上限；
\item $\alpha$--$\beta$ 模型判断跨地址空间数据移动的 latency/bandwidth 代价；
\item load balance 与 critical path 决定这些局部成本最后怎样落到 wall time 上。
\end{itemize}
任何一个模型都只覆盖其中一层，不能互相替代。

\toprule

\section{并行分析方法}

面对一个新的数值 kernel，可以按下面顺序分析，而不是先选择编程接口：
\begin{enumerate}
\item 固定数学语义，明确这一阶段真正要产生哪些输出；
\item 选择最小有意义的 logical task，并写出 $R_t$ 与 $W_t$；
\item 区分 RAW 真依赖与由存储复用产生的 WAR/WAW，判断哪些依赖可以通过重命名、双缓冲或算法改写消除；
\item 构造 computation DAG：明确节点、依赖边和初始 ready set，估计 $W$、$S$ 与 $W/S$，并检查是否存在能减少关键路径的等价算法或状态表示；
\item 决定 task aggregation 粒度，并区分逻辑所有权、物理放置与执行分配；
\item 找出跨所有权读取、冲突写和全局聚合，把它们分别映射为 load、atomic、barrier、halo 或 collective；
\item 估计 FLOPs、bytes、message count、message volume、reduction depth 与 load imbalance；
\item 最后才选择 OpenMP、CUDA、MPI 或异构组合，并用 profiler 验证实际瓶颈是否与模型一致。
\end{enumerate}

这套流程的价值在于，它把“并行程序为什么慢”分成可证伪的几类原因。若 $W/S$ 已经很低，问题在算法结构；若 $W/S$ 很高但单 kernel 受 bandwidth 限制，问题在数据移动；若局部 kernel 很快但总体扩展差，则应继续检查同步、通信、负载不均和粗层并行度，而不是继续只优化算术指令。

\section{本章小结}

本章首先把 computation DAG 建立为并行分析的核心对象：节点是逻辑任务，边是必须保持的先后关系，ready set 描述当前真正可执行的任务，critical path 的代价就是 span。由此可以明确区分两件事：DAG 决定算法暴露了多少并行性，scheduler 只负责把已经 ready 的任务映射到有限执行资源。

更重要的是，DAG 不是数学问题唯一自带的一张图。算法选择、状态版本、存储组织和任务分解都可能改变依赖结构。Prefix sum 展示了最清楚的例子：线性递推的 span 为 $\Theta(N)$，而 work-efficient tree scan 在保持 $\Theta(N)$ work 的同时把 span 降到 $\Theta(\log N)$。后续 Jacobi、RBGS、reduction、halo overlap 与 V-cycle 都可以回到同一问题：哪些依赖边是真正不可消除的，哪些可以通过算法或表示重构去掉。

\section*{习题}

\subsection*{计算题}
\begin{enumerate}[label=\arabic*.]
\item 对式~\eqref{eq:parallel-small-dag}的四任务 DAG，写出每一步可能的 ready set；分别在 $P=1$ 与 $P=2$ 时给出一个合法 schedule，并计算完成时间。
\item 一个 DAG 有 64 个单位工作 task，关键路径长度为 8。计算 $W,S,W/S$，并分别给出 $P=4,8,32$ 时由式~\eqref{eq:parallel-lower-bound}得到的时间下界；再用式~\eqref{eq:parallel-brent-bound}给出贪心调度的上界。
\item 比较串行递推、Hillis--Steele scan 与 work-efficient tree scan 的 $W$、$S$ 和 $W/S$。解释为什么 Hillis--Steele 的平均并行度可以更高，却不因此成为 work-efficient 算法。
\item 某程序固定问题规模下的串行比例为 $s=0.04$。计算 $P=8,32,128$ 时 Amdahl 模型的理想 speedup 与 efficiency，并说明 $P\rightarrow\infty$ 时的极限。
\item 用 $T=\alpha+\beta m$，取 $\alpha=2\,\mu s$、带宽 $1/\beta=20\,\mathrm{GB/s}$。比较发送一个 $8\,\mathrm{MB}$ 消息与发送 1024 个总量同为 $8\,\mathrm{MB}$ 的小消息的模型时间，忽略 overlap。
\item 一个 kernel 每个元素做 18 FLOPs，从瓶颈内存层实际搬运 64 B。计算 arithmetic intensity；若可持续带宽为 $200\,\mathrm{GB/s}$、峰值算力为 $4\,\mathrm{TFLOP/s}$，求 Roofline 上界并判断它更可能受哪一侧限制。
\end{enumerate}

\subsection*{推导与证明题}
\begin{enumerate}[label=\arabic*.]
\item 证明任何调度都必须满足 $T_P\ge W/P$ 与 $T_P\ge S$，从而得到式~\eqref{eq:parallel-lower-bound}。再说明贪心调度为何可得到式~\eqref{eq:parallel-brent-bound}的数量级上界。
\item 对原地三点更新 $x_i\leftarrow x_{i-1}-2x_i+x_{i+1}$，判断相邻任务之间分别是否存在 RAW、WAR 与 WAW；再说明引入只读旧数组 $x^{old}$ 与独立新数组 $x^{new}$ 后哪些依赖消失。
\item 证明若每个输出位置具有唯一 writer，且所有输入在阶段开始前已经就绪，则纯 gather kernel 不需要为输出写入设置互斥锁。
\item 用三个浮点数量构造一个 $(a+b)+c\neq a+(b+c)$ 的例子，并解释它为什么意味着并行 reduction 的“无 data race”并不保证 bitwise reproducibility。
\item 给出一个 scatter kernel 的 write--write 冲突例子，并分别说明 atomic、privatization 和改写为 gather 如何改变其执行结构。
\end{enumerate}

\subsection*{编程与上机题}
\begin{enumerate}[label=\arabic*.]
\item 实现串行 prefix sum、Hillis--Steele scan 与 work-efficient tree scan。对 $N=8$ 输出每一轮状态，画出 computation DAG，并用实测同步轮数验证 span 的数量级。
\item 对一维 stencil 比较“一点一个调度任务”和“固定长度 tile 一个调度任务”，测量不同问题规模下的调度开销、带宽与负载均衡。
\item 实现串行 reduction 与 tree reduction，改变线程数并检查浮点结果末位是否发生变化，同时记录 wall time。
\item 使用 profiler 或硬件计数器测一个低算术强度 kernel，比较实测带宽与 Roofline 预测；若偏差很大，继续检查同步、粒度和 load imbalance。
\end{enumerate}

\subsection*{工程与综合题}
\begin{enumerate}[label=\arabic*.]
\item 给定一个新的数值 kernel，按“Problem $\rightarrow$ Algorithm $\rightarrow$ Computation DAG $\rightarrow$ Ownership/Placement $\rightarrow$ Schedule $\rightarrow$ Machine”的顺序写出并行化诊断报告。必须明确 DAG 的节点、边、ready set 与关键路径，不允许先从 OpenMP/CUDA/MPI API 开始描述。
\item 某优化把 FLOPs 降低 30\%，却让主存流量增加 2 倍。结合式~\eqref{eq:parallel-cost-decomposition}与 Roofline 分析它在哪些机器条件下可能更慢。
\item 比较“按数据块固定 owner”和“动态抢 task”两种策略，分别讨论 locality、load balance、reproducibility 与调度成本。
\item 某 MPI 程序把 blocking halo 改成 nonblocking halo 后几乎没有加速。利用本章模型列出至少三种可验证原因，并说明应该观测什么证据来区分它们。
\end{enumerate}
